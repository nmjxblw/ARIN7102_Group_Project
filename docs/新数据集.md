# 新评估测试集构建说明

## 背景与动机

旧测试集（`eval_dataset_llm.json`，100 条）存在三个缺陷：

1. **只有单病 case**：90% 为单病单症状，无法测出 dual-recall 在多病场景下的融合效果
2. **每条只有 1 个 relevant drug**：Precision@K 天花板系统性偏低，评估噪声大
3. **"others" 污染**：部分 case 的 disease 是 `others`，BERT 不会预测该类，label recall 必然失败

---

## 数据来源

| 数据 | 路径 | 用途 |
|---|---|---|
| 药表 | `match_data_preprocessing/data/enhanced_drug_table_v1_structured.csv` | 候选药物 + 评分 |
| BERT decomposition | `app/dataset_module/drugs_training_dataset/eval_dataset_llm_v2.json` | 63k 条真实用户 review + BERT 标签，作为 query 来源 |
| DDI 数据库 | `data/db_drug_interactions.csv` | RAG 上下文，辅助 LLM 评估药-药交互 |

## Stage 1：候选生成（本地，无 LLM）

文件：`app/evaluation/build_test_set.py`

### 流程

**1. 加载药表**
- 过滤掉 disease 为 `"others"` 的记录，保留 37 个真实疾病类别
- 计算 business_score = `avg_rating × log1p(total_reviews)`，用于同疾病内部排序

**2. 加载 query**
- 从 v2 json 读取 sentence（symptom_text）+ BERT 分解出的 diseases / symptoms
- 去重，丢掉含 `"others"` 的 case
- 按 disease 数量分桶：
  - single（1 个 disease）：34,773 条
  - double（2 个 disease）：2,964 条
  - triple+（3+ 个 disease）：60 条

**3. 分层抽样**

| 桶 | 数量 | 占比 |
|---|---|---|
| single | 150 | 50% |
| double | 100 | 33% |
| triple+ | 50 | 17% |

合计 300 条，其中 entangled（多病）占 50%。

**4. 为每条 case 选 relevant_drugs**
- 对每个 disease，从药表里取 top-N 候选药（N=3）
- 排序键：`(symptom_overlap, business_score, -len(diseases))`
- 第 1 名：`relevance_score=3`，其余：`relevance_score=2`
- 最终每条 case：single→3 药，double→6 药，triple+→9 药

**输出**：`data/eval_dataset_candidates.json`（300 条）

## Stage 2：LLM 医学验证

文件：`app/evaluation/verify_test_set.py`

使用 **MiniMax-M2.5** 模型（reasoning model），通过 `extra_body={"reasoning_split": True}` 将推理链与最终 JSON 输出分离，避免 `<think>` 内容混入响应。

### Prompt 设计

每条 case 向 LLM 提问三件事：

1. **drug_disease_match（0–3）**：该药是否实际治疗所述疾病？
2. **drug_symptom_match（0–3）**：该药是否缓解所述症状？
3. **contraindication_risk（0–3）**：该药对所列任意疾病是否有禁忌？（0=无风险，3=绝对禁忌）
4. **ddi_risk_overall（0–3）**：候选药池整体的药-药交互风险（pool-aware 语义，见下方说明）

LLM 返回严格 JSON 结构：

```json
{
  "drugs": [
    {"name": "...", "disease_match": 3, "symptom_match": 2,
     "contraindication_risk": 0, "rationale": "..."}
  ],
  "ddi_risk_overall": 1,
  "ddi_rationale": "..."
}
```

DDI 上下文通过 `app/evaluation/ddi_context.py` 从 `db_drug_interactions.csv` 按药对检索，作为 RAG 上下文注入 prompt，避免 LLM 凭空猜测。

### Pool-aware DDI 语义

relevant_drugs 是**检索候选池**，不是同服处方。LLM 被明确告知：按"临床医生从池中合理选择一个子集"的最坏情况评估 DDI，而非假设所有药同时服用。

### 保留规则

每个药逐一判断：
- **保留**：`disease_match >= 2` 且 `contraindication_risk <= 1`
- **丢弃**：不满足以上条件，从 relevant_drugs 中移除

若某条 case 的所有药均被丢弃 → 整条 case 丢弃（`all_drugs_failed_threshold`）。

**DDI 不作为过滤条件**，仅写入 case 的 `ddi_flags` 字段作为 metadata：

```json
"ddi_flags": {
  "overall_severity": 2,
  "rationale": "propranolol + verapamil major AV-block risk",
  "checked_subset_semantics": "pool"
}
```

### 并行执行

使用 `ThreadPoolExecutor(max_workers=15)` + `threading.Lock` 并行调用 LLM，`tqdm` 进度条实时更新。

**输出**：
- `data/eval_dataset_verified.json`：最终测试集
- `data/verification_log.jsonl`：每条 case 的 LLM 原始回复 + 保留/丢弃原因（审计用）

## 最终结果

| 类别 | 数量 |
|---|---|
| 候选生成（Stage 1） | 300 条 |
| LLM 验证通过（ok） | 191 条（63.7%） |
| 全药未过阈值丢弃 | 74 条（24.7%） |
| API 连接错误 | 31 条（10.3%） |
| JSON 解析失败 | 4 条（1.3%） |
| **最终测试集** | **191 条** |

疾病分布：single ~50%，double ~33%，triple+ ~17%（分层抽样保持比例）。

## 与旧测试集对比

| 维度 | 旧集合（100 条） | 新集合（191 条） |
|---|---|---|
| entangled case 比例 | ~10% | ~50% |
| 每条 relevant drugs 数 | 1 个 | 3–9 个 |
| "others" 污染 | 有 | 无（已过滤） |
| LLM 医学验证 | 无 | 有（disease_match + contraindication） |
| DDI 标注 | 无 | 有（ddi_flags metadata） |
